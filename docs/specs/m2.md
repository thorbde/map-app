# M2 plan: data and sign-in

- **Status:** a plan, waiting for Thor's answers to the five questions below. No code yet.
- **Written:** 2026-11-18, while M1 is being finished.
- **Spec:** `docs/specs/mvp.md` §3, and the M2 row in `KICKOFF.md`. **Decisions:** ADR 0006 (D1), ADR 0007 (Google only, the test-only sign-in), ADR 0003 (access; its gate is built in M4).

## Goal

In the spec's words (`KICKOFF.md`): **"You can sign in with Google with an invite code and pick a username, on a preview deploy."**

What M2 covers: the database (Drizzle on D1, migrations, a database per PR preview), Better Auth with Google, the test-only sign-in for e2e tests, invite codes, and `/onboarding` with a username and a display name.

**Not in M2:** essays (M3); profile pages, settings, visibility, export, delete account and `access.server.ts` (M4); admins and the production database (M5).

## What already exists

### In the repo: less than the docs suggest

M0 and M1 built **no database and no sign-in**. Checked in the code on `main`, 2026-11-18:

- `app/server/` holds one file, `platform/worker.ts`. There is no `db/`, no `access.server.ts`, no env validation, and `platform/index.server.ts` doesn't exist yet. `ARCHITECTURE.md` describes them as the plan.
- `wrangler.jsonc` has no database binding. `drizzle-orm`, `drizzle-kit`, `better-auth` and `zod` are not installed. `pnpm db:generate` and `pnpm db:migrate` are in `CLAUDE.md` but not in `package.json`.
- **What is there:** preview deploys per PR in the separate Previews account (`.github/workflows/preview.yml`), whose token already has "D1: Edit" (`KICKOFF.md`); tests running in workerd (`apps/web/vitest.config.ts`); e2e against a local build only (`apps/web/playwright.config.ts`); and `Button`, `Field` (label, description, error), `Link` and `Dialog` in `@thorbde/ui`. The floating Panel comes with M1 PR 5.

### What the libraries already do

Read from the published packages (`better-auth` 1.7.26, `drizzle-orm` 0.45.4) and Cloudflare's docs, on 2026-11-18. Each PR's plan re-checks its own part.

| Need | Already provided by | We use it? |

**What they leave out:** Better Auth sends no usage data unless switched on (checked: off by default). By default it stores Google's access tokens and the profile picture's address; we need neither (question 5).

### How two established products do it

- **Duolingo:** the account exists straight after sign-in, with a username it made up, changeable later. Profiles are [public by default](https://duolingoguides.com/how-to-make-your-duolingo-profile-private), with a switch in settings.
- **Strava:** asks for a name during sign-up. Profiles and activities are [visible to everyone by default](https://www.tomsguide.com/wellness/fitness/how-to-adjust-your-strava-privacy-settings) for adults, with privacy controls in settings. It has been criticised for that default for years.

**What we take:** one short step after the first sign-in, nothing else before the app. **Where we differ, on purpose:** the writer picks the username (it is their public address, and can't be changed in the MVP), and question 3 recommends private as the default.

### What we build ourselves

The table of invite codes and its check, the username rules and reserved list, the `/onboarding` page, and the fences around the test-only sign-in. If question 4 is answered as recommended, an ADR names the `username` plugin and says why it isn't used (`CLAUDE.md`, "Before you build").

## Questions for Thor

"All recommended" is a complete answer.

### 1. How does Google sign-in work on PR previews?

Google only answers to addresses registered in advance, exactly, and each PR's preview has its own address.

- **A, one fixed helper address.** A copy of `main` runs at a fixed address in the Previews account. Google answers there, and it hands the sign-in on to the PR's preview (Better Auth's OAuth Proxy). You register one address with Google, once.
- **B, no Google sign-in on PR previews.** Only the fixed copy of `main` has it. You try sign-in after merging, not before.
- **C, you add each PR's address in Google's console by hand.**

**Recommended:** A. If the plugin turns out not to work with a preview as the fixed address, we fall back to B and tell you, instead of working around it.

### 2. Is the invite code asked for before or after Google?

- **A, before.** The sign-in panel has a field for the code beside "Continue with Google". Without a valid code no account is created, so we store nothing about people who weren't invited. People who already have an account skip the field.
- **B, after.** Anyone can sign in with Google, then must enter a code. We'd hold the name and email of people who never get in.

**Recommended:** A.

### 3. Who can see a new account's map: everyone, or only its owner?

The setting to change it arrives in M4, so M2 has to pick the starting value.

- **A, "Only me".** Nothing is public until the writer says so. This is what GDPR calls data protection by default.
- **B, "Everyone",** as on Duolingo and Strava.
- **C, ask during onboarding.** One more choice on the first screen.

**Recommended:** A. C can be added in M4, when there is something to show.

### 4. Usernames: our own few lines, or Better Auth's username plugin?

Your rule is not to reinvent, so this is yours to decide.

- **A, our own.** The username sits with the rest of the profile (name, bio, visibility), as `ARCHITECTURE.md` has it. About 30 lines: the pattern, the reserved list, and the database's own guarantee that no two are alike. An ADR records why the plugin isn't used.
- **B, the plugin.** It exists for signing in with a username and password, which we don't have. It would keep the username in the sign-in tables, apart from the profile, and add two addresses we'd have to switch off. The reserved list would still be ours.

**Recommended:** A.

### 5. What do we keep from the Google account?

- **A, name and email only.** No profile picture (the spec shows none anywhere), and Google's access tokens are not stored (we never call Google again after sign-in). ADR 0007 is updated: it says "name, email and avatar URL".
- **B, everything Better Auth stores by default,** including the picture's address and the tokens.

**Recommended:** A. Less to protect, less to export and delete in M4.

### To be shown in Storybook, not asked here

- **The sign-in panel:** the invite-code field, its error, and "Continue with Google".
- **The Google button.** Google's rules ask for its "G" logo on the button. That is a trademark, not an icon from a library, but it is a second mark beside our own icons (`DESIGN.md`), so you see it before it is used.
- **The onboarding step:** username and display name, with the helper text and each error (taken, reserved, too short, wrong characters).
- **Where "Sign out" lives,** and what a signed-in person sees in the panel's header.

## Risks worth your attention

### Privacy and EU data

- **An account row holds a real name and email.** With question 2 as recommended, only invited people get one. Emails are never shown to others and never written to logs (the Worker's logging is on).
- **The database is stored and run in the EU; the Worker is not pinned there.** A request can be handled at any Cloudflare location, so data passes through memory outside the EU on its way. ADR 0006 accepted this; it matters again for the schools item in `roadmap.md`.
- **Google sees every sign-in.** That comes with ADR 0007.
- **Preview databases hold real Google accounts** (yours, when you try a preview). They are created in the EU too, and deleted with the PR.

### What can't be undone

- **A merged migration** is never edited (`CLAUDE.md`). PR 1's is read with extra care; mistakes after that cost a new migration, not a rewrite.
- **Usernames.** Fixed for each person in the MVP. The reserved list should be generous from the start: reserving a name later doesn't free it from whoever took it.
- **The EU setting of a database** is chosen when it is created. The production database is created in M5, by you.
- **Nothing in M2 touches production.** No production database, secret or migration.

### What you create yourself

Agents never read production secrets, and can't sign in to Google's console. For M2 you need the **preview** set only; production's own set comes in M5.

1. **A Google sign-in client for previews** (about ten minutes, [Google Cloud console](https://console.cloud.google.com/apis/credentials)):
   - Create a project, for example "Memogra previews".
   - "OAuth consent screen": type External, app name "Memogra", your email. Scopes: only `openid`, `email`, `profile`. Leave it in "Testing" and add your own Google address as a test user.
   - "Credentials" → "Create OAuth client ID" → "Web application". Two redirect addresses, which PR 3 gives you exactly: the fixed helper's (question 1) and `http://localhost:5173/api/auth/callback/google` for running locally.
2. **Three repository secrets** (GitHub → Settings → Secrets and variables → Actions): `PREVIEW_GOOGLE_CLIENT_ID`, `PREVIEW_GOOGLE_CLIENT_SECRET`, and `PREVIEW_AUTH_SECRET` (a random value: run `openssl rand -base64 32`).
   - These are readable by any PR's workflow, like the preview Cloudflare token. That is why they belong to a client that only previews use, and production gets a different one (ADR 0006's reasoning).
3. **Nothing else.** The preview Cloudflare token already allows D1.

### Limits and costs

- **10 databases on the free plan,** in a Previews account shared by all your apps: at most about ten open PRs with a preview at once. Since September 2026 the free plan also stops queries when the day's quota is used up. If either bites, Workers Paid on the Previews account is about 5 USD a month.
- **10 ms of CPU per request** on the free plan. Sign-in does some cryptography; PR 3 measures it on the preview.

### For the sessions that build this

- **Cloud sessions can't reach `better-auth.com` or `orm.drizzle.team`.** Either Thor allows both hosts in the `map-app` environment, or the session reads the installed package's own type files, as this plan did.
- **An agent can't sign in with Google.** Agents test through the test-only path (PR 4); only Thor can check the real thing, on a preview. Ask him early in PR 3.
- **The rename to Memogra:** the Google consent screen says "Memogra" from the start. Worker and database names stay `map-app-…` until Thor renames them (`m1.md`, "Still open").
