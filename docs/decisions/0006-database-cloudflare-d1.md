# 0006: Database: Cloudflare D1 instead of Neon Postgres

- **Status:** accepted
- **Date:** 2026-11-15
- **Supersedes:** the database part of ADR 0001

## Context
ADR 0001 picked Neon Postgres. During kickoff we looked again at what the database costs us day to day:

- **A second vendor and account,** plus a Neon API key in CI so every PR and every test run can get its own database branch.
- **The access-test matrix (ADR 0003)** needs a real database in CI, which with Neon means a network call to a cloud branch on every run.
- **Local development** needs a personal Neon dev branch and a connection string.

The app's data is small: a few hundred users at most for a long time, with one short text essay per country.

## Decision
- **Use Cloudflare D1** (SQLite managed by Cloudflare), accessed through a Worker binding and **Drizzle** (`drizzle-orm/d1`).
- **Create every database with `--jurisdiction=eu`.** D1 then stores and runs the database inside the EU. This can only be set when a database is created, never afterwards.
- **Environments:**
  - **local:** `pnpm dev` uses a local D1 (a SQLite file under `.wrangler/`). No account needed.
  - **tests:** the Vitest Workers pool gives each test file an isolated D1 with the migrations applied. No secrets and no network.
  - **preview:** CI creates one D1 per PR, applies the migrations and deletes it when the PR closes. A preview **never** binds the production database (enforced as below).
  - **production:** one D1, written to only by the deploy from `main`.

### Keeping previews away from production
A rule is only as strong as what enforces it. Cloudflare API tokens can't be limited to a single D1 database, and a PR can change its own workflow files, so any token a PR workflow can read must not be able to reach production. Therefore:

- **Previews live in a separate Cloudflare account** (free plan, shared by all of Thor's apps). Each PR gets its own Workers, `map-app-pr-<number>` for the app and `map-app-storybook-pr-<number>` for Storybook, deployed by `.github/workflows/preview.yml` and deleted when the PR closes. Storybook for `main` stays at `map-app-storybook` (`.github/workflows/storybook.yml`). The build runs in a job without the token; only the deploy job has it. Its token is a repository secret (`CLOUDFLARE_PREVIEW_ACCOUNT_ID`, `CLOUDFLARE_PREVIEW_API_TOKEN`). Even a broken or malicious PR workflow can only touch preview resources.
- **The production token is a secret of a GitHub `production` environment** whose deployment rule allows only `main`. Production deploys and migrations run in their own workflow, triggered by pushes to `main`. Jobs for PRs can't read that secret.
- **Preview databases are named `memogra-pr-<number>`** (new Cloudflare resources are named `memogra-…`, Thor, 2026-11-27), and `.github/scripts/preview-database.sh` refuses to create, migrate or delete anything else, as a guard against mistakes. `pnpm db:names` (in `pnpm check`) tests that guard, and fails if the deployed config binds a database or a workflow names any other `memogra-…` database.
- **The production database ID appears only in the production section of the wrangler config.**
- **Migrations** are generated by `drizzle-kit` and applied with `wrangler d1 migrations apply`.

### Rules that keep a later move to Postgres cheap
D1 has **no interactive transactions** (no `BEGIN … COMMIT`). Its atomic unit is a **batch**: a list of statements that all succeed or all fail, where a statement can't use the result of an earlier one. So:

1. **All database access goes through Drizzle,** in each feature's `queries.server.ts`. No raw SQL strings elsewhere.
2. **IDs are generated in the app** (`crypto.randomUUID()`), never by the database. Then a batch can insert a row and reference its ID in the same batch.
3. **Multi-step writes use `db.batch([...])`** and compute derived values in SQL. For example, `essay_count` is set with an `UPDATE … SET essay_count = (SELECT COUNT(*) …)` in the same batch.
4. **No SQLite-specific features** (no `json_extract` in queries, no `PRAGMA`, no SQLite-only functions). JSON columns are stored as text and validated with zod when read.
5. **Timestamps are stored as integers** (Unix milliseconds, `integer({ mode: "timestamp_ms" })`) and booleans as Drizzle booleans, so they map cleanly to Postgres types later.

**Named exception (M2 PR 1, Thor, 2026-11-18):** Better Auth's tables are kept exactly as its CLI generates them, and their `created_at` / `updated_at` columns default to SQLite's clock, `cast(unixepoch('subsecond') * 1000 as integer)`. That is a SQLite-only function in the schema. It's allowed only there: Better Auth sets these times itself, so the default rarely runs, and a move to Postgres regenerates these tables with Better Auth's Postgres schema anyway. Our own tables set times in the app.

### How it's wired (M2 PR 1)
- **Local and tests:** the binding `DB` (database `memogra-local`) is in the `local` environment of `wrangler.jsonc`, not at the top level, so the deployed config has no database; previews get theirs from CI (below). `pnpm dev` (`CLOUDFLARE_ENV=local`), the tests and `pnpm db:migrate` (`wrangler d1 migrations apply DB --local --env local`, the flags fixed in the script) select it.
- **Previews (M2 PR 2):** the deploy job of `preview.yml` creates `memogra-pr-<number>` with `--jurisdiction=eu` on the PR's first deploy and reuses it after that, applies the migrations that haven't run (`wrangler d1 migrations apply --remote`, with a config that names only that database), and adds the `DB` binding to the built Worker's `wrangler.json`. The build job never sees it. The cleanup job deletes it when the PR closes; reopening starts with an empty database.
- **At the limit of databases** (10 on the free plan, shared by all of Thor's apps), creating fails and so does the deploy, with an error that lists the preview databases in the account. A preview is never deployed without its database. Nothing deletes databases automatically beyond the PR's own: the account holds other apps' databases too.
- **Settings are checked when the database is first asked for** (`getDatabase()` in `server/platform/index.server.ts`), not on every request, so a deploy without a database still serves the pages that don't need one.

## Alternatives considered
- **Neon Postgres (ADR 0001):** stronger long-term (a richer SQL dialect, real transactions, database branching) and portable to any host. More moving parts today for no current need.
- **Local Postgres in Docker for tests, Neon for deploys:** removes the CI secret, but two database setups to maintain.
- **Turso (libSQL):** SQLite with branching, but another vendor. D1 is already in the Cloudflare account we need anyway.

## Consequences
- **One vendor fewer.** Local development and tests need no database account at all.
- **Portability to Node gets harder.** D1 only exists on Cloudflare. Leaving Cloudflare means moving the database too: to plain SQLite or libSQL (small change, same dialect) or to Postgres (see below).
- **Switching to Postgres later** means rewriting `server/db/schema.ts` with `pgTable`, regenerating migrations, swapping the batches for transactions, and writing a one-off data copy script. If the rules above are followed, that's days of work, not weeks.
- **Package sizes:** `drizzle-orm` and `drizzle-kit` are recorded, with their sizes, in the M0 toolchain ADR before any code depends on them.
- **Free-plan limits** (database count, storage, rows read and written per day) are far above what the MVP needs. CI must delete preview databases when PRs close, because the number of databases per account is capped.
- **The D1 binding** is a Workers API, so it is only touched in `server/platform/`. The rest of the app receives a Drizzle client.
